# 叩き台(イニシャルWBS)の作り方と点検

企画発表資料(10/27夕方に受け取る)から、採用企画ごとの叩き台を作る手順と、品質をそろえるための基準。氏名入りの資料はコミットしない。作った叩き台(企画名・内容を含む)も、公開リポジトリには置かない(置くのは見本だけ)。

## 作る手順(10/27夜)
1. 資料から、企画ごとに次の6点を抜き出す: ①何を作るか ②だれのどんな困りごとか ③主な機能 ④使う技術・道具 ⑤ハード(機材)の有無 ⑥発表資料に書かれた不確かな点(未決の点)。
2. 種別を決める(下の型): ソフト/ハード/映像・デザイン/ゲーム/AI・データ。2つ以上にまたがる企画は主たる型+足す項目。
3. 見本(`docs/wbs-drafts/example-soft.md`)の粒度で、6大項目の下に **50〜60項目** を書く。
4. `npm run check-draft -- <ファイル> [--hard]` で点検し、✗ をなくす。△ は理由があれば残してよい。
5. 16企画ぶんを一覧にして、教員が10/28の朝に確認 → キックオフ画面の「叩き台」に貼って取り込む(貼ると同じ点検が画面にも出る)。

## 成果物を軸にする
卒研の成果物(中間報告・最終報告・卒展)の一覧は `docs/deliverables.md`。叩き台は、これを背骨にして作る。
1. 成果物1つにつき、「作る」項目を、決まった大項目に入れる(題名は成果物の名前で)。期限は deliverables.md の表のとおり。
2. 「確かめる」項目(レビュー・テスト・読み合わせ)も、必要なものは足す。
3. 企画ごとの項目(企画発表資料から)は、成果物を作るための中身として足す。成果物と企画で食い違う点は、推測せず「決めること」として項目にする。
4. 点検が、成果物の抜けを誤りとして知らせる(ハード系は回路図、ソフト系はER図・テーブル定義書も)。

## 形式(必須)
- `#` 大項目は、雛形の6つを順に: 企画の具体化 / 要件定義 / 外部設計 / 内部設計・実装 / テスト・検証 / 発表・展示準備。
- `-` が項目(2階層目)。さらに分けるときだけ、インデントで3階層目。
- 詳細は、`> やること: …` と `> できあがり: …` の2行。ヒント・例・やり方は書かない。担当(@)や題名の日付(〜11/30)は書かない(担当は空欄)。
- **期間は、はじめから入れる**: 各項目に `> 期間: 2026-11-02〜2026-11-10` の行を付ける(いちばん下の項目だけ。親は子から決まる)。書いていない項目は、キックオフ画面(「期間のない項目に、期間を自動で入れる」)か `npm run check-draft -- <ファイル> --fill` が、大項目ごとの時期の中に順に並べて入れる。入れたあとは、企画に合わせて人が直す。
- 親になる項目(下に項目がある項目)は、詳細は不要。

## 品質の基準(点検で見ている/人が見るところ)
| 基準 | 中身 |
|---|---|
| 題名 | 「何を」まで入る動詞つき。32字まで。「検討」「調整」だけは不可 |
| できあがり | 「完了と言える状態」。作ったもの・数・確認した人のいずれかが入る。「完了」「できる」だけは不可 |
| 順序 | 各大項目の中は、実際にやる順に並べる(学生は上から着手する) |
| 粒度 | 1項目は、1人が数日〜1週間で終わる大きさ。大きすぎれば分け、細かすぎれば束ねる |
| 偏り | どの大項目も3件以上、1つの大項目が全体の35%を超えない |
| 企画らしさ | 「機能1を実装する」のような汎用の題名は、企画の機能名に置き換える(見本は汎用のままなので、必ず直す) |
| 節目 | 下の表の節目が、項目として入っている |

## 型ごとに足す・厚くする項目
- **ソフト(Web・アプリ)**: 見本のとおり。画面と機能を、企画の言葉で分ける。公開・動作環境の確認を入れる。
- **ハード(機材発注あり)**: 要件定義に「予算と部品の洗い出し」。内部設計・実装に「回路/構造の設計」「部品の発注(11/5)」「追加発注(12/1)」「組み立て」「配線・はんだ」「ソフトとの結合」。発注前に「教員へ部品表を出す」。納品待ちの間にできる作業(ソフト側・外装設計)を別項目にして、手待ちを減らす。テストに「電源・安全・耐久の確認」。
- **映像・デザイン**: 外部設計に「絵コンテ・デザインカンプ」。実装を「制作」と読み替えず、題名は「撮影する」「編集する」「素材を作る」。テストは「見る人に見てもらう」。
- **ゲーム**: 外部設計に「ルール・操作・レベル設計」。実装に「プロトタイプ(コアの遊び)を先に作る」→「ステージ/コンテンツを足す」。テストに「遊んでもらってバランスを直す」。
- **AI・データ**: 要件定義に「データの入手方法と使ってよい範囲」「評価の指標」。実装に「データの準備」「モデルを試す」。テストに「指標で評価する」「失敗例を調べる」。

## 精度を上げるために、あらかじめ決めておくとよいこと(教員へ)
- 資料(PPTX推奨)に、機能・技術・必要な機材が書かれていると精度が上がる。書かれていない点は、叩き台の「企画の具体化」に「決めること」として項目にする(推測で機能を作らない)。
- ハード系かどうかは、資料に機材が出ているかで判断する。迷うものは教員に確認する。
- 16企画の統一感: 項目数と粒度は、点検で同じ基準にそろえる。

## 期間の決め方
- 自動で入る期間は、大項目ごとの時期(企画の具体化 10/28〜11/6、要件定義 11/2〜11/16、外部設計 11/9〜11/25、内部設計・実装 11/16〜1/15、テスト・検証 12/14〜1/22、発表・展示準備 12/21〜2/5)に、項目を順に並べたもの。あくまで初期値なので、企画の中身(作る量・機材の納期)に合わせて、10/27夜に私が直す。
- 節目の期限(外部設計レビュー11/25、発注11/5・12/1、最終レビュー1/26、動画1/27、内覧会1/28、提出2/2、卒展2/6)を越える期間は、点検で誤りになる。
- 点検は、期間のない項目・授業期間(10/28〜2/6)の外・開始が終了より後・節目の期限超え・45日を超える長い項目を見る。
